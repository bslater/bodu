# Core & Collections — Structural and Hot-Path Assessment

**Date:** 2026-07-17
**Scope:** `Bodu.Core/src/` (439 files), `Bodu.Collections/src/` (149 files), `Bodu.Collections.Concurrent/src/` (27 files) — ~79k lines.
**Focus:** poorly designed types and implementation problems, with an emphasis on structural improvements and hot-path optimisation — the same remit as `crypto-hashing-structure-hotpath-assessment.md` and `text-serialization-structure-hotpath-assessment.md`.

## Relationship to prior reviews

This is the deeper follow-up pass the forensic review explicitly did not perform for these packages: `docs/forensic-review/07-numerics-calendar-financial.md` gave `Bodu.Core` and `Bodu.Collections` only "a lighter structural pass", and `03-concurrency.md` went deep solely on the threading/concurrent slice. Its resolved items are not re-litigated here:

- **R1** (AsyncDebouncer CTS dispose race) — re-confirmed fixed and intact; `TryCancel` swallows `ObjectDisposedException` with the correct rationale, and #626's only touch on the file was a doc reflow.
- **R9** (grant-vs-cancel policy) — re-confirmed: "success-wins" is now uniform across all the `Bodu.Threading` primitives, documented and test-pinned.
- **R10** (Vyukov non-power-of-two caveat) — re-confirmed properly documented on the class and at `SlotIndex`.
- WS-3's cleared hypotheses on the ring (seqlock protocol, ABA immunity, slot padding, allocation-free fast paths) all still hold.
- **`ConcurrentHashSet<T>` was reviewed fresh**: WS-3's verdict ("faithful ConcurrentDictionary port, lock-striping") describes a design that no longer exists — the type was rewritten as a lock-free split-ordered list (#615). The rewrite verifies clean on its core protocol (mark-folded deletion CAS, per-generation `Core` making `Clear` linearizable, benign grow/publish race exactly as documented); findings below are edge/doc-level.

Baseline for this pass: the solution builds clean and BVT is green across the three scope test projects (Core 23,293 / Collections 3,442 / Concurrent 752).

This pass asked the round's standing question: *is the code well-structured, and does it run as fast as its careful cores deserve?* Every High finding below was independently re-verified against the cited source by a second pass before inclusion.

## Overall verdict

The load-bearing cores are genuinely well engineered — hand-traced RB-tree fixups and order-statistic maintenance are correct, the Vyukov ring and the new split-ordered set are textbook-quality lock-free code, the tick/day-number arithmetic and the PRNG's debiased bounded draws are exact, and XML documentation across the catalogue is unusually honest. The problems cluster into three themes:

1. **Stamped-out twins have already drifted into divergent bugs.** The DateTime/DateOnly quarter engine is duplicated verbatim and its two copies produced two *different* `LastDateOfWeekInQuarter` bugs; the `EvictingDictionary` eviction core was hand-copied into the concurrent Segment so its comparer bug exists twice; one folder holds four hand-copied RB-tree fixup cores; the Evicting/Sequenced dictionaries duplicate ~500 lines of view/versioning boilerplate that has already diverged behaviourally.
2. **Comparer and contract discipline break at the seams, not the cores.** LFU frequency buckets compare keys with default equality while the store uses the injected comparer (corrupting eviction, and in the concurrent variant permanently poisoning it); `RangeSet<T>`'s read side re-validates with `Comparer<T>.Default` and throws for any custom-ordered set; MRU touch skips the version bump its sibling performs and silently truncates enumeration; trie prefix queries skip fail-fast versioning entirely; and several class-level docs promise the opposite of the implementation (in-place reversal, preserved eviction metadata, deferred `Randomize`, a finite `Leibniz`).
3. **Hot paths pay avoidable per-operation costs.** LFU cache reads are O(bucket) linear scans; every LRU/MRU hit allocates a fresh linked-list node; every casing-converter call rebuilds a 38-entry acronym dictionary; every ring operation pays a non-constant integer division; every `foreach` over a trie materializes the whole collection; every `OrderedSet` removal rehashes the entire table; and the fiscal provider resolves the same fiscal year ~4× per call.

Severity keys: **High** = fix promptly (wrong result likely in normal use, hang/corruption, or order-of-magnitude perf), **Medium**, **Low**.

## What is right (re-confirmed)

- **The tree cores are correct.** RB insertion/deletion fixups, rotation size-transfer, phantom-leaf size/Max repair ordering, and the interval-tree `Max` early-break were hand-traced clean, as were floor/ceiling/higher/lower, rank/select, and `CountInRange` edge semantics. Range views stream in O(log n + k).
- **The lock-free code is high quality.** The Vyukov ring's seqlock protocol, ABA immunity, and padding all re-verify; the split-ordered `ConcurrentHashSet` rewrite is a genuinely well-built Shalev–Shavit implementation (mark-folded deletion markers, cooperative unlinking, idempotent sentinel adoption, 64-bit-widened keys, a per-generation `Core` making `Clear` linearizable, and the grow/publish race correctly neutralized in code and docs). Lock discipline in the striped dictionary is simple and deadlock-free, with eviction events strictly post-commit and user code kept out of stripe locks.
- **Shared-core layering where it exists eliminates drift**: `TrieCore`/`RadixTrieCore`/`AhoCorasickCore` back the generic/non-generic twins with zero duplication (the best structural decision in the collections tree), and `OrderedSetStorage` cleanly serves both ordered sets. Radix invariants are pinned by a 10k-op seeded differential sweep against the uncompressed-trie oracle; Aho-Corasick is textbook-correct and allocation-free per scanned character.
- **The arithmetic and algorithmic cores are exact**: the tick/day-number engine (400/100/4-year cycles, allocation-free decomposition), the custom ISO week-of-year logic (verified traces at year boundaries), `XorShiftRandom`'s Lemire debiased bounded draws, the probabilistic sketches' m/k and w/d derivations, HLL's small-range correction, and Fraction-grade overflow pre-checks in the sequence generators.
- **The Option/Result/Either trio is exemplary struct design** — total `default` semantics with documented rationale, strict/lenient lifts consistently named, `GetValueOrThrow` preserving the captured exception as `InnerException` — and the async extension conventions (synchronous validation, `ConfigureAwait(false)`, state-machine-skipping fast paths) are uniform. `ThrowHelper`'s live partials are hot-path clean: `AggressiveInlining` throughout, resx lookup and formatting only on the throw branch, no boxing.
- **Discipline is the norm, not the exception**: eager-validation/deferred-iterator splits across the operator family, fail-fast versioning with struct enumerators on nearly every collection, lazy-`StringBuilder` unchanged-input fast paths in the string surface, comparer preservation on copy/ctor paths everywhere outside the LFU buckets, `NaturalStringComparer`'s allocation-free ordinal-and-numeric compare, and honest member-level weak-consistency documentation in the concurrent trio that is well above typical library standard.

- **C10 `Aggregate` "byte-identical bodies" — scope corrected.** On inspection the indexed/non-indexed overload pairs have textually similar bodies but dispatch to *different* func arities, so they are distinct capabilities, not redundant duplicates. Only the genuinely divergent seedless-indexed overload (which seeded with `default(TSource)`, unlike LINQ) was removed; the remaining ten are kept.
- **C11 ring trim-policy — declined (defect not present).** The finding described `Deque` neutralising `CircularBuffer`'s trim policy after construction; in the current code `Deque` pre-computes its capacity and passes it *into* the base constructor, so the base trim path is simply never triggered for `Deque` — there is no post-hoc neutralisation to refactor away, and the five ring partials are already `sealed`/interface-consistent. No change.
- **C12 `MultiValueDictionary.ValueComparer` — declined (not dead surface).** On inspection the comparer genuinely drives value identity (`IndexOfValue`, `ContainsValue`, `Remove`, novelty filtering) under the `Set` value backing; it is inert only under the default `List` backing, where it is already documented as such. Removing it would break the Set-backing semantics and its tests, so the surface is retained and the List-backing caveat left documented.
