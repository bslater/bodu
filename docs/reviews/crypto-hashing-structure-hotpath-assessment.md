# Cryptography & Hashing — Structural and Hot-Path Assessment

**Date:** 2026-07-15
**Scope:** `Bodu.Security.Cryptography/src/` and `Bodu.IO.Hashing/src/` (347 source files).
**Focus:** poorly designed types and implementation problems, with an emphasis on structural improvements and hot-path optimisation.

## Relationship to the forensic review

This is a **deeper follow-up pass** to `docs/forensic-review/01-cryptography.md`, not a replacement. That review assessed the two libraries for *exploitable* conditions and rated them "ship-quality — no Critical or High severity issue" on the security axis, and that verdict holds: the constant-time discipline, verify-before-release AEAD, and zeroization coverage it confirmed are real and were re-confirmed here.

This pass asked a different question — *is the code well-structured and does it run as fast as its careful cores deserve?* — and found substantially more to fix. The forensic review deliberately did not fault hot-path throughput or type-design duplication; those are exactly this document's subject. Where the two overlap (e.g. the Ed25519 duplicate small-order check, tracked as forensic R11), this document defers to the existing remediation item.

## Overall verdict

The **layering is fundamentally sound and already span-first** — there is no array-based legacy interface to migrate, RFC fidelity is traceable line-by-line, and the correctness-critical details are handled deliberately rather than incidentally. The problems cluster into three themes:

1. **Glue layers throw away the optimised cores.** The engines (keystream generation, field arithmetic, block permutations) are well-tuned, then the transform/mode/finalisation layer around them processes byte-at-a-time, allocates per block, or re-runs one-shot setup per block. The AES-AEAD stack and the non-crypto hash hot loops are the worst offenders.
2. **Stamped-out duplication that has already drifted.** Seven per-family cipher `*Transform` shells, four byte-identical asymmetric `KeyMaterial` classes, a five-level CRTP ladder whose type parameter is never used, and two parallel padding stacks with *different* side-channel profiles.
3. **A handful of genuine safety/correctness traps** — none a confirmed cryptographic break, but each makes a dangerous mistake the easy path: use-after-dispose keystream reuse, a silently-ignored `Mode` setter, nonce reuse as the default call sequence, and a constant-time claim ML-DSA's rounding code does not honour.

Severity keys below: **High** = fix promptly (safety or order-of-magnitude perf), **Medium**, **Low**.

## What is right (re-confirmed)

- **Layering and span-first surface.** `IBlockCipher → IBlockCipherModeTransform/IAeadBlockCipherModeTransform → IPaddingStrategy → BlockCipherTransform`; engine → transform → algorithm for stream ciphers; HPKE facade → sender/receiver → context → key schedule → labeled KDF → KEM. All span-based; no legacy array interface to migrate.
- **Constant-time discipline is real, not aspirational:** branchless PKCS7/ISO7816-4 unpad, masked GHASH, `FixedTimeEquals` tag checks everywhere, ML-KEM's branch-free implicit rejection (`ConstantTimeDifference` + arithmetic-mask select, without round-tripping through `bool`), X25519 mask-driven cswap + all-zero-secret rejection, Ed25519 S≥L malleability and strict canonical decoding with the cofactorless divergence explicitly documented.
- **Verify-before-release AEAD** with output cleared on tag mismatch; one-shot AEAD transforms latch `_completed` in `finally` even on failure; CTR counter-wrap latching throws instead of reusing keystream.
- **Zeroization is generally excellent** — stackalloc'd subkeys/keys cleared in `finally` throughout; the gaps in A5 are the exceptions that prove the rule.
- **The suspected `XSalsa20Poly1305` / `XSalsa20Poly1305Aead` duplication is the opposite** — a clean, well-factored split with the two framings isolated in `Poly1305AeadCore`.
- **`Crc` finalisation/resume math** (reflect-in/out asymmetry, XOR-undo ordering, sub-byte widths) and **`HashingStream`** decorator are correct and cleanly factored; **Luhn** and **IBAN** are verified correct against spec.

## Remediation roadmap

Three phases, sequenced by value-per-line and risk. Every fix is test-first; existing tests are the immutable behavioural contract (behaviour-preserving hot-path work is locked with new pinning tests first, then optimised digest-identical).

### Phase 1 — Safety & contract fixes (small, independent diffs)
Dispose guards on mode transforms and stream engines (A1, A11); `Mode`→`BlockMode` sync with a shared switch-based enum mapper (A2); nonce-reuse guard on `SymmetricStreamAlgorithm` (A3); the five zeroization gaps (A5); `CrcStandard` `init`→`get` + drop `ISerializable`, `Crc.ComputeHash` reset, `InvalidOperationException` for reconfiguration, volatile `GlobalCache` (A6/A7/A9/A11); doc/endianness/OTP-cap/XTS corrections (A8, A10).

### Phase 2 — Hot paths (highest throughput return)
Widen `IBlockCipher` with `EncryptBlocks`/`DecryptBlocks` default methods and cache the AES ECB transform (B1, B12); CLMUL GHASH/POLYVAL with the scalar fallback (B2); Blake3 span-into-reusable-state, delete `Shake.KeccakF`, lane-wise `KeccakSponge` (B3, B4); chunked XOR + Poly1305 span core (B5, B6); direct-from-source deferred-final (B7); slicing-by-8 CRC, deferred-modulo Fletcher, fix Adler SIMD, stream Murmur/SuperFastHash (B8, B9); then the second tier — ML-KEM/ML-DSA workspaces, cached Ed25519 point, span `PadBlock`, hoisted Scrypt buffers, cached HPKE AEAD (B10–B13).

### Phase 3 — Structural consolidation
De-CRTP both hash ladders (C1); collapse the seven `*Transform` shells + hoist shared `Mode`/`BlockMode`/`Padding` plumbing (C2); `RawKeyAsymmetricAlgorithm` base + single `AsymmetricKeyMaterial` + `LatticeCommon` (C3); re-parent Skein/CubeHash and make ML-DSA rounding branch-free (C4, A4); delete dead surface / decide the value-type integration (C5); collapse the check-digit hierarchy and slim `IResumableHashAlgorithm` (C6); naming decisions for `Serpent`/`XSalsa20Poly1305Aead` (C7).

### Verification
`dotnet build bodu.slnx` + `dotnet test … bvt.runsettings` after every step; full `regression.runsettings` (Wycheproof/ACVP for ML-KEM/ML-DSA, RFC vectors for AEAD/stream ciphers, the CRC catalogue) after hot-path changes; the `Bodu.Security.Cryptography.Simd.Test` assembly re-verifies scalar fallbacks whenever SIMD dispatch changes.

## Remediation outcome

All three phases were implemented on this branch, one green commit per logical step (build + BVT after every commit; the regression/ACVP tiers and the SIMD-disabled assembly after hot-path and dispatch changes). Findings whose remediation was assessed and **deliberately declined** are recorded here so the disposition is auditable:

|---|---|
| A1–A11 | **Fixed.** A4's branch-free `Power2Round`/`Decompose`/`MakeHint`/`InfinityNorm` verified digest-identical against the ML-DSA ACVP vectors. |
| B1–B13 | **Fixed**, with three assessed-and-declined subitems: the Poly1305 span core (B6 — the AEAD framing already processes in 4 KB chunks, so the array-API copy is bounded); a full ML-DSA workspace flatten (B10 — the Â matrix reaches ~57 KB for ML-DSA-87, which does not belong on the stack; ML-KEM's ≤ 4 KB workspaces were flattened); CTR keystream batching (B12 — marginal after the AES key-schedule cache landed). |
