# Reference `.msg` fixtures

These binary fixtures are third-party Outlook message files used only to
validate the `Bodu.Formats.Outlook.Msg` reader against an independent
real-world corpus. They are redistributed here under their original
permissive license, whose full text is carried alongside in
[`LICENSE.Apache-2.0.txt`](LICENSE.Apache-2.0.txt).

## Provenance

| Folder / files | Source | License |
|---|---|---|
| `valid/*.msg`, `invalid/*.msg` (41 files) | [`apache/poi`](https://github.com/apache/poi) — `test-data/hsmf/` (trunk, retrieved 2026-07-31) | Apache-2.0 — Copyright The Apache Software Foundation |

The corpus spans the producer variations the synthetic fixtures cannot:
code pages 950 / 1251 / 1252 / 20127 / 28591 / 65001, string and binary
HTML bodies, compressed-RTF bodies, attachments (inline images, PDF,
nested messages), the non-mail message classes (appointment, contact,
post, sticky note, task), a 1,321-recipient message, and Office-writer
quirks (submission-chunk variants, missing recipient addresses).

The `invalid/` files are two fuzzer-minimized inputs whose containers are
structurally malformed; the reader must reject them with
`OutlookMsgFormatException`. The third fuzzer-minimized file in the
upstream set opens cleanly and therefore sits under `valid/`. Files under
`valid/` must open and decode under `CompoundValidationLevel.Compatible`;
they are deliberately **not** required to pass `Strict` — tolerating
real-world writers is the Compatible contract.

## Manifest

[`manifest.json`](manifest.json) records the per-fixture expectations the
`OutlookMessageReferenceCorpusTests` Regression sweep asserts: SHA-256 of
each file, the declared code page, subject, sender name, recipient and
attachment counts, and body presence. The expectations were generated by
an **independent implementation** — `olefile` 0.47 (structure and raw
streams) plus a small mechanical extraction script — so the sweep is a
cross-implementation check, not a self-confirmation. Counts were
additionally cross-checked with `msg_parser` 1.x; its two disagreements
(`cyrillic_message.msg` recipients, `lots-of-recipients.msg` recipients)
were adjudicated in olefile's favor by a third independent count and by
this package's reader agreeing with olefile. Subjects recorded with
U+FFFD replacement characters come from files whose declared code page
(UTF-8) does not match their actual string bytes — a real-world writer
defect the sweep asserts loosely (non-null) rather than byte-exactly.
