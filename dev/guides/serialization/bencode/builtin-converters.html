Built-in converter catalog

Every type that BencodeSerializer handles without a user converter is served by a built-in converter - internally an ordinary BencodeConverter<T>. This page catalogs that set - which .NET types are provisioned, how each is represented on the wire, and what the read path accepts. Resolution order and the rules for overriding a built-in with your own converter are covered in Writing converters.

The library follows the design shared across the Bodu serializers: exact-type scalar converters first, factories for open type families (nullables, enums, dictionaries, collections, plain objects) last, with the document object model bridges ahead of everything so a DOM value is never claimed by a structural factory.

Bencode (BEP 3) has exactly two scalar forms - integers and byte strings - and the built-in set deliberately covers only types with a native mapping. Boolean, floating-point, char, Guid, Uri, Version, TimeSpan, and the date-time types are not provisioned: serializing one without a registered converter surfaces a missing-converter error rather than silently inventing a lossy representation. See Pattern 5 in Writing converters for the bridging recipe.

Structural and document-model types

Nullable<T> underlying type's form Bencode has no null; a null member is omitted before any converter runs.

BencodeDocument the document's root A deserialized document is caller-owned: dispose it to return its pooled buffer.

Public enum converters

Registered on the options or referenced from a [Converter(...)] attribute:

  • BencodeStringEnumConverter / BencodeStringEnumConverter<TEnum> - member-name byte strings with an optional naming policy and integer-on-read flag.
  • BencodeNumberEnumConverter<TEnum> - the underlying numeric value as a Bencode integer.

An integer read as an enum, by the default handling or by either converter, must lie within the range of the enum's underlying type: one outside it raises BencodeSerializationException at the integer's offset rather than being narrowed into the type, so i300e never binds a byte-based enum as 44. An integer inside the range binds whether or not it names a member, and an enum based on ulong reads integers up to ulong.MaxValue, which BencodeNumberEnumConverter<TEnum> also writes.

Names are matched as System.Text.Json's JsonStringEnumConverter matches them, by the default handling and by the string-enum converter alike. A member's wire name, from [StringEnumMemberName] or the converter's naming policy, binds only in its own case. The CLR name of a member that [StringEnumMemberName] does not rename also binds, in any case, but a renamed member's CLR name does not: with [StringEnumMemberName("on")] on Enabled, 2:on binds, and 2:ON, 7:Enabled and 7:enabled do not. A combination of flags is written as the comma-separated wire names of its flags, in the order Enum.ToString lists them, so under NamingPolicy.SnakeCaseLower CanRead | CanExecute is 21:can_read, can_execute. It is read from such a list in any order, each name trimmed of white space, with a trailing comma tolerated but no empty name anywhere else. A list holds names only: an integer binds, where integers are allowed, only as the whole byte string, so 4:1, 4 is rejected.

A string-enum converter created with allowIntegerValues: false reads names only, as System.Text.Json's JsonStringEnumConverter does from .NET 9. It rejects a Bencode integer, and a byte string that holds one too: a byte string that is not a member's wire name and has an integer in any of its comma-separated parts (an optional sign and the digits 0 to 9, ignoring white space around them), such as 1:2, 4: +2 or 7:Read, 2, raises BencodeSerializationException at the byte string's offset rather than binding the integer. The wire names are matched first, so a member renamed with [StringEnumMemberName("1")] still reads from 1:1. The default handling, and a converter that allows integers, bind a byte string that is an integer, such as 1:2, as the integer it holds. On write, such a converter refuses a value that is neither a member nor a combination of defined flags, such as (Status)99 or a flags value with an undefined bit, and raises BencodeSerializationException rather than writing the decimal text it would reject on read; the default handling, and a converter that allows integers, write it as that text, 2:99.

An enum used as a dictionary key follows the same names, as System.Text.Json's enum converter reads and writes a property name. A key is written by its wire name, a combination of flags by its flags' wire names, and any other value as its decimal text, whatever the rule for integer values, so with [StringEnumMemberName("on")] on Enabled a Dictionary<Toggle, int> writes the key 2:on, reads it back, and rejects 7:Enabled with BencodeSerializationException. Where a BencodeStringEnumConverter handles the key type, keys also follow its naming policy and its rule for integer values, so with allowIntegerValues: false the key 1:1 is rejected. Otherwise, under the default handling or BencodeNumberEnumConverter<TEnum>, keys are written by name with no naming policy, and integer text binds.

Types that need a user converter

Capability Bencode
Native scalar kinds integer, byte string
Types needing a representation decision none - byte strings are native binary
Types served only by a user converter bool, floating-point (double / float / decimal), char, Guid, Uri, Version, TimeSpan, the date-time types
Document root any value kind
object / element / document bridges yes

Each of the converter-only types maps cleanly onto an integer or a byte string - see Pattern 5 in Writing converters and Pattern 6 in Using Bencode for worked bridges.
