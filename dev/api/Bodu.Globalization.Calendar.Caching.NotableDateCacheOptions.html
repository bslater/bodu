ThrowOnStorageFailure

Gets or sets a value indicating whether a storage read or write failure is surfaced as an exception rather than degrading to an empty read or a skipped write.

public bool ThrowOnStorageFailure { get; set; }

Property Value

bool

true to rethrow the underlying storage failure; false (the default) to keep the best-effort behaviour the INotableDateCache contract describes.

Remarks

The default keeps a cache fault from breaking notable-date resolution, which suits most consumers. Set it for a deployment that must not run with a silently broken cache. Argument validation always throws regardless of this setting.

The failure is rethrown as the store produced it rather than being translated, so a caller handles the pair the cache treats as a storage failure: IOException and UnauthorizedAccessException. Which of the two a given fault yields is the storage layer's choice and varies by platform - a blocked file write surfaces as IOException on Unix and UnauthorizedAccessException on Windows - so code that catches only one will miss the other.

ValidateStorageOnStart

Gets or sets a value indicating whether the cache eagerly probes its backing store when constructed and throws when the store is unusable, rather than deferring the discovery to the first read or write.

public bool ValidateStorageOnStart { get; set; }

Property Value

bool

true to probe the store at construction; false (the default) to skip the probe.

Remarks

The SQLite and distributed dependency-injection packages run this probe through their ValidateOnStart wiring, so a misconfigured store fails the host start; a cache constructed directly probes in its constructor instead. This setting is independent of ThrowOnStorageFailure.
