Remarks

CRCs are the workhorse of integrity checks in storage, networking, and file formats: every .zip, .png, Ethernet frame, USB packet, and Modbus message uses one. Each protocol bakes in slightly different choices - polynomial, initial value, input/output bit reflection, final XOR - and the same byte sequence can produce a different digest under CRC-16/ARC, CRC-16/MODBUS, or CRC-32/ISO-HDLC. Rather than ship a class per variant, Crc consumes the parameters from a CrcStandard and the same engine computes the right answer for every catalogue entry.

Picking a standard. The full RevEng catalogue is exposed two ways:

  • CrcStandard static properties For the common entries (CRC32_ISOHDLC, CRC32_ISCSI, CRC16_MODBUS, …) - direct, allocation-free references to the canonical instance.
  • Get(CrcStandards) with a CrcStandards enum value For programmatic look-up across the full catalogue (e.g. when reading a configuration value).
  • FromName(string) Resolves both canonical names and aliases - "CRC-32", "PKZIP", "CRC-32/ISO-HDLC" all return the same instance.

API surface. Crc derives from NonCryptographicHashAlgorithm and exposes the standard Append(ReadOnlySpan<byte>) / Reset() / GetCurrentHash() shape. The NonCryptographicHashAlgorithmExtensions companion adds one-shot ComputeHash, stream variants, and constant-time VerifyHash / TryVerifyHash on top.

Snapshot semantics. The final reflection, XOR-out, and width mask are applied to a copy of the running accumulator, so GetCurrentHash() can be called as often as the caller likes without disturbing further Append calls - useful for emitting progressive checksums of an unfinished stream.

Resumption. Crc implements IResumableHashAlgorithm: given a previously emitted digest and additional bytes, it produces the digest of the concatenated input without needing the original bytes back - handy for log-tail integrity checks and content-addressed storage. Resumption is only valid against a digest produced by an instance configured with the same CrcStandard.

Performance. Lookup tables are precomputed once per (width, polynomial, reflectIn) tuple and shared via GlobalCache, so creating multiple Crc instances for the same standard is cheap. The hot path uses byte-at-a-time table lookups; for throughput-critical code consider re-using a single instance and feeding it large spans rather than repeatedly constructing new ones. Instances are not thread-safe; share behind explicit synchronization.

important

CRC is not cryptographically secure. It detects accidental corruption, not adversarial tampering - collisions are easy to construct. Use a member of Bodu.Security.Cryptography or HashAlgorithm for password hashing, digital signatures, message authentication, or any context where a determined attacker could choose the input.

using System.IO.Hashing;
using Bodu.IO.Hashing;
using Bodu.IO.Hashing.Checksums;
using Bodu.IO.Hashing.Extensions;

// 1. Standard PKZIP / Ethernet CRC-32 of a buffer.
var crc32 = new Crc(CrcStandard.CRC32_ISOHDLC);
byte[] digest = crc32.ComputeHash(File.ReadAllBytes("payload.bin"));

// 2. Modbus RTU - different polynomial/init/reflect choices, same engine.
var modbus = new Crc(CrcStandard.CRC16_MODBUS);
modbus.Append(frameHeader);
modbus.Append(framePayload);
byte[] frameCrc = modbus.GetCurrentHash(); // non-destructive snapshot

// 3. Resumption - fold an appended log segment into yesterday's digest without re-reading
// the original bytes.
var resumable = (IResumableHashAlgorithm)new Crc(CrcStandard.CRC32_ISOHDLC);
byte[] updated = resumable.ComputeHashFrom(digest, File.ReadAllBytes("payload.appended.bin"));

Remarks

State is reset after finalization as well as before, matching the reset-before-and-after semantics of the shared ComputeHash extension (GetHashAndReset). This keeps the instance reusable for a subsequent Append(ReadOnlySpan<byte>) without the prior input bleeding into the new digest.
